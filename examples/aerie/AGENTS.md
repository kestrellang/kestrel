# Aerie (Kestrelcraft) style guide

How code in `examples/aerie` is written. Follow it for every change here;
when touching a file that breaks it, leave that file a little closer to it.

## Objects own their behavior

- Behavior lives as methods on the type that owns the data: `world.raycast(...)`,
  `state.encode()`, `padded.mesh()`, `Daylight.at(phase)`. A free function
  is only for something with no natural owner (a tiny math helper).
- One responsibility per type and per file. If describing it needs "and",
  split it. `Renderer` orchestrates; the passes (`ChunkPass`, `ModelPass`,
  `OverlayPass`) each own their pipelines and buffers.
- Group state that changes together into a small struct with its own
  methods (`FpsCounter`, `Notice`, `Breaking`, `Settings`). A type with a
  long field list is several types.
- Resource owners (GPU objects, the game) are `not Copyable` so they can't
  be duplicated by accident. Plain data is a copyable value type.
- Constructors that can fail or do work are `static func` (`Renderer.create`,
  `Settings.fromEnvironment`); `init` only assigns.

## SOLID, in this codebase

- **Single responsibility**: see above.
- **Open/closed**: a new block, bird or pass is a new enum case or type plus
  one registration. Keep each `match` over a kind in one place, ideally a
  method on the enum (`Block.hardness`, `BirdKind.model`).
- **Liskov**: a protocol conformance keeps the protocol's promises; no
  "not supported" traps.
- **Interface segregation**: take the smallest thing a function needs (a
  `Generator`, a `Vec3`), not the whole `Game`.
- **Dependency inversion**: game logic computes and sets flags
  (`wantsSave`, `mouseCaptured`); the driver (`main.ks`, `platform.ks`)
  touches files, windows and the browser.

## Flat control flow

- Guard clauses first: handle trivial and failing cases with `guard ... else
  { return }` or an early `return`, then write the main path unindented.
- At most two levels of indentation inside a function body. Deeper code
  becomes a named method.
- Prefer `match` and `let x = if/match ...` expressions over if/else ladders
  and assign-in-branches.
- Prefer `for x in items` and `for i in 0..<n` over manual `while` index
  loops. Use `while` only when the loop's step isn't a simple count.
- Functions fit on a screen (about 40 lines) and either orchestrate (call a
  few named steps) or do detail work, not both.
- Four parameters at most; past that, group them into a struct. No `Bool`
  parameters that switch behavior: make two methods or an enum.

## Data and constants

- One source of truth. A fact is stored once and everything else derives
  from it: shader constants come from `shaderHeader`, `src/ui/ui.ks` is
  generated by `tools/make_ui.py`, GPU struct sizes come from
  `Layout.of[T]().size`, never a hand-counted number.
- Name every number that isn't obviously 0, 1 or 2, with its unit in the
  name or doc comment (`dayLength` "seconds in one day").
- `let` by default; `var` only when it changes. Smallest scope wins.

## Naming and comments

- Names say what, in plain words: `isVisible`, `slotSize`, `untilAutosave`.
  Booleans read as questions or states (`isEmpty`, `wantsSave`, `gliding`).
- Every type, field and function has a `///` doc in plain English, giving
  units and ranges ("0 to 1 over a day").
- Comments explain why, not what. If a comment restates the code, rename or
  extract until it doesn't need to.

## Layout

- `src/game/` play, `src/world/` blocks and islands, `src/render/` the GPU
  side, `src/ui/` the interface; `main.ks` and `platform.ks` drive it.
- Dependencies flow one way: game uses world, render and ui; render and ui
  read world types but never game state; world depends on nothing here.
- Shaders live in `assets/shaders/*.wgsl`, never as strings in Kestrel.

## Review checklist

Refactor before merging if a function needs scrolling, goes deeper than two
levels of indentation, takes more than four parameters, or its name needs
an "and".
